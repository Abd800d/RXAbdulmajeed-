# APH V2 — الخطة التنفيذية المعتمدة

## القرارات المعتمدة

- **تطبيق الهاتف الجديد:** Flutter، مع إبقاء تطبيق React/Capacitor وملف APK الحالي متاحين أثناء الانتقال.
- **الخلفية:** Supabase (PostgreSQL/Auth/Storage/Realtime) بوصفه مصدر البيانات المركزي، مع **FastAPI** كبوابة API آمنة للبحث المتقدم وRAG والاستيراد والتكاملات.
- **لوحة الإدارة:** تطوير لوحة React الحالية تدريجياً بدلاً من التخلص منها.
- **البحث:** PostgreSQL `pg_trgm` وFull Text كمسار موثوق أول، مع واجهة جاهزة لإضافة Meilisearch عند وصول البيانات إلى الحجم الذي يستدعي ذلك.
- **الأسرار:** لا يوجد مفتاح مزود داخل Flutter أو APK أو JavaScript. مفاتيح الذكاء والرؤية وخدمة Supabase تحفظ على الخادم فقط.

## حدود الخدمات

### Flutter

- واجهة عربية/إنجليزية وRTL/LTR وMaterial 3.
- SQLite/Drift للبيانات المتزامنة والمفضلة والطوابير غير المتصلة.
- مزامنة تزايدية بمؤشر `catalog_change_feed.sequence`، وليست تنزيل مليون سجل دفعة واحدة.
- بحث محلي في السجلات المخزنة وبحث خادمي في القاعدة الكاملة.
- Barcode وOCR محلي ثم مطابقة خادمية عند الاتصال.
- لا يتصل بمزودي AI أو Google باستخدام أسرار مباشرة.

### FastAPI

- API ثابت الإصدار تحت `/v1`.
- التحقق من JWT الصادر من Supabase للوظائف الخاصة.
- البحث والتصفية والتزامن وRAG وعمليات الاستيراد الطويلة.
- Rate limiting عبر Redis مع بديل محدود داخل العملية للتطوير فقط.
- دعم Meilisearch خلف واجهة Repository دون جعل التطبيق معتمداً عليه.
- OpenAPI تلقائي واختبارات عقدية.

### Supabase/PostgreSQL

- المصدر الرسمي للسجلات المعتمدة.
- فصل المادة الفعالة عن المنتج والسوق اليمني.
- توثيق المصدر على مستوى الحقل وتاريخ التحقق.
- أدوار: `owner`, `admin`, `pharmacist_editor`, `reviewer`, `support`, `user`.
- حالات مراجعة واعتماد، وسجل قديم/جديد لكل تعديل.
- Storage للصور والوثائق والمرفقات، مع روابط موقعة للملفات الخاصة.
- Realtime للتنبيهات والمحادثات ومؤشر تغييرات الكتالوج.

## مسار الاعتماد

```text
Draft → Pending review → Approved → Published
                    ↘ Rejected
Published → Archived/Unpublished → public tombstone/change event
```

- المحرر ينشئ مسودة أو يرسل للمراجعة.
- المراجع يعتمد أو يرفض مع ملاحظة.
- النشر فقط يجعل السجل متاحاً للمستخدم العام.
- تبقى النسخة السابقة في `catalog_revisions` و`audit_log`.
- حذف/إخفاء السجل يولد حدث DELETE للمزامنة كي يُحذف من الأجهزة.

## مطابقة البدائل

لا تسجل علاقة بديل معتمد إلا بعد التحقق من:

1. جميع المواد الفعالة وترتيبها.
2. تركيز كل مكوّن ووحدته.
3. الشكل الصيدلاني.
4. طريق الإعطاء.
5. مراجعة صيدلي.

تُعرض درجة الثقة وأسباب التطابق وتنبيه أن الاستبدال قرار صيدلي/سريري.

## مراحل التسليم

### المرحلة 1 — الأساس (قيد التنفيذ)

- مخطط V2 والأدوار والمصادر والمراجعة والمزامنة.
- مشروع Flutter قابل للبناء بهوية APH ولغتين وقاعدة Drift.
- مشروع FastAPI بعقد `/v1` واختبارات وأمن أساسي.
- CI مستقل للويب وFlutter وAPI.

### المرحلة 2 — بيانات وإدارة

- شاشات CRUD للجداول الجديدة.
- قائمة مراجعة واعتماد.
- معالج استيراد: معاينة، ربط أعمدة، أخطاء، ZIP صور، واسترجاع.
- إدارة ATC والمصادر والوكلاء والموردين.

### المرحلة 3 — بحث وتعرف

- اقتراحات وتصحيح ومرشحات متقدمة.
- Meilisearch عند الحاجة واختبارات مقارنة جودة.
- Barcode/OCR متعدد المراحل ونسب تطابق وتأكيد المستخدم.
- بدائل آمنة ومعتمدة.

### المرحلة 4 — RAG ومراسلة

- استرجاع السجلات المعتمدة ومقاطع المصادر فقط.
- إجابات موثقة وتاريخ مصدر ودرجة ثقة.
- محادثات خاصة، مرفقات مفحوصة، تنبيهات، وإعلانات.

### المرحلة 5 — الإنتاج

- اختبارات مليون سجل وفشل/استئناف/تراجع.
- اختبارات أمان وRLS وملفات ضارة ومعدلات الطلب.
- مفاتيح توقيع Android Release ثابتة وبناء APK/AAB.
- سياسة خصوصية وشروط واختبار استعادة النسخ الاحتياطية ومراقبة.

## تعريف الإنجاز النهائي

لا يُعد APH V2 منجزاً لمجرد خروج APK. الإنجاز يعني أن Flutter وFastAPI وقاعدة البيانات ولوحة الإدارة وStorage والبحث وRAG والمزامنة والنسخ الاحتياطي تعمل معاً ضد بيئة إنتاج فعلية، وأن اختبارات الأمان والاستيراد والاستعادة موثقة وناجحة.
